# Cosmos Removal — starthn .NET API → stateless compute microservice

Replicated the horizon-frontend migration: the starthn Azure Functions API no longer
touches Cosmos DB. It is now a stateless compute microservice (translate / LLM-review /
chat / contact). The Cloudflare Worker (D1 + R2) is the system of record; it forwards
source content to Azure and persists returned results.

## New ProfileFunctions / TranslateUserPage contract
Stateless. Auth via `InternalAuth.Verify(req, _config)` (shared secret `X-Internal-Auth`);
no Cosmos-backed user auth, no `IUserService`, no `IUserPageTranslationRepository`.
Request body: `{ Languages: string[], Bio: string?, PageContent: string? }`.
For each language it calls `TranslationService.TranslateUserPageAsync(bio, pageContent, lang)`
and returns `{ translations: { [lang]: PageTranslation } }`. The edge persists to D1.

## Edge page-translate handler decision — UPDATED (yes, it needed changes)
Previously the edge handler just proxied the original request (only `{ Languages }`) to Azure
with `X-Internal-Auth` + `X-User-Id`, relying on Azure to read bio/pageContent from Cosmos,
persist translations to Cosmos, and return the dict. With Azure now stateless this no longer
works, so `src/server/routes/profile.ts` was updated to mirror horizon's handler:
1. read `bio`/`pageContent` from D1 (`UserRepository.getById`),
2. POST `{ languages, bio, pageContent }` to Azure,
3. upsert the returned per-locale translations into the `user_page_translations` D1 table
   (page_content JSON-encoded), returning the translations map.
Auth (`requireAuth`) and the rest of the profile routes are unchanged.

## Auth on the 3 translate functions
Blog/Category/Tag/Profile translate functions all already used `InternalAuth.Verify(req, _config)`
(no Cosmos-backed permission helper existed in starthn), so no AuthHelper/permission/Cosmos

## Where starthn genuinely differed from horizon
1. **LLM provider lookup cascade.** starthn read the LLM provider/model from Cosmos at runtime
   via `LlmProviderService` (+ repos + AutoMapper) for both translation review and chat. horizon
   takes the provider config per-request from the edge. To reach zero Cosmos this whole chain was
   deleted and `LlmReviewService`/`ChatService` converted to horizon's stateless forms. This is
   beyond the literal task list but required by the delete-cascade / "match horizon" / zero-Cosmos.
2. **Chat env provider.** starthn used the `Azure.AI.OpenAI` SDK for the env Azure OpenAI path;
   horizon uses raw HTTP. Adopted horizon's raw-HTTP approach so the SDK package could be removed.
   Start HN's chat system prompt was preserved verbatim.
3. **Entity content type.** starthn's `BlogPostEntity.Content` / `BlogPostTranslationEntity.Content`
   are `List<object>` (horizon: `List<string>`). Kept starthn's shapes — BlogService/BlogFunctions
   use `.Cast<object>().ToList()` accordingly.
4. **csproj PropertyGroup.** Kept starthn's `<RuntimeIdentifier>linux-x64</RuntimeIdentifier>` +
   `<SelfContained>false</SelfContained>` (starthn-specific deploy target; horizon has neither).
   Only the package ItemGroup was changed.
5. **server.ts.** Kept starthn-specific apex→www redirect, spam-guard matchers, `image-handler`,
   and its inline `handleD1PrimaryRoute` (horizon factored these differently / uses image-warm).
   Only the sync import + `/api/internal/sync` route were removed.
